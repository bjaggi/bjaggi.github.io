    How the broker count is calculated

    We take your five inputs, apply Event Sizer’s hidden host assumptions, compute how many brokers each resource needs, then recommend the largest of those numbers (never below 4). Two-DC/AZ architecture doubles that capacity count.

    Your inputs

    1. Throughput — producer ingress I in MB/s (the slider).

    2. Retention — how many days to keep data.

    3. Tiered storage — optional. If on, only hot days stay on local disk; the rest is object storage and does not add brokers.

    4. Two DC Architecture — optional. If selected, the capacity count is doubled so either data center or AZ can fail.

    5. Disk storage — usable TB on each broker (default 12). This is not the broker count.

    Assumptions we do not ask for

    Replication factor = 3. Egress = ingress. TLS on. Size at 60% of host capacity. Baremetal host: 24 cores, 64 GB RAM, 10 GbE (1,250 MB/s), 1× SSD at 520 MB/s. CPU ≈ 120 MB/s produce per broker before the 60% target. Production floor = 4 brokers. Rebuild time and partition count are not specified, so they do not raise the count.

    The result

    capacity_brokers = max(4, network, IO, storage, CPU, RF) brokers = capacity_brokers × (2 if Two DC Architecture is selected, otherwise 1)

    Each line below is “how many brokers this resource alone would need.” Cluster Size highlights the winner — that is the limiting resource. Example at the defaults (50 MB/s, 7 days, 12 TB/broker, no tier): storage needs 8, everything else needs 1–4, so we recommend 8 brokers, or 16 for two DCs/AZs.

    From throughput, retention, and disk → storage brokers

    local_days = hot_days if tiered is on, else retention hot_GB = I × 1,000,000 × local_days × 86,400 × 3 / 1,000,000,000 storage = ceil(hot_GB / (disk_TB × 1,000))

    Three copies of the local window must fit on broker disks. Larger I, more retention (or more hot days), or smaller disk_TB all increase this number. Tier storage uses the same formula without the × 3 and does not add brokers.

    From throughput → network brokers

    cluster_net_MB/s = I × 3 network = ceil(cluster_net_MB/s / (1,250 × 0.60))

    Produce, replication, and consume share a 10 GbE card, used at 60%.

    From throughput → IO brokers

    disk_write_MB/s = I × 3 IO = ceil(disk_write_MB/s / (520 × 0.60))

    Each replica is written to disk. 520 MB/s is Event Sizer’s SSD guideline, used at 60%.

    From throughput → CPU brokers

    CPU = ceil(I / (120 × 0.60))

    TLS is on. About 120 MB/s of produce per broker before the 60% target.

    From replication / HA (no extra input)

    RF = 3    high availability = at least 4

    RF 3 needs three brokers for replicas. We add a spare, so the count never goes below 4 even if throughput and disk would fit on fewer.

    Resource utilization (after broker count is known)

    network % = cluster_net_MB/s / (brokers × 1,250) IO % = disk_write_MB/s / (brokers × 520) storage % = hot_GB / (brokers × disk_TB × 1,000) CPU % = I / (brokers × 120)

    Share of raw host capacity at the recommended broker count. This is not the 60% target used when sizing.
