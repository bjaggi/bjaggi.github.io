What this tool estimates

The sizer recommends a self-managed Apache Kafka / Confluent Platform broker count and disk from peak throughput, retention, optional tiered storage, and usable disk per broker.

Broker count uses Event Sizer granular’s max(...) of HA, network, disk IO, local disk, CPU, and replication factor. Recommendations appear when a dimension is binding.

The inputs

InputWhat it means
1. Throughput Peak produce ingress in MB/s (1–1000). Size on the busiest sustained rate, not the daily average.
2. Retention How long to keep data (1–365 days). With tiered storage off, all of this lives on local broker disk.
3. Enable tiered storage Checkbox. When on, recent data stays on local disk and older data goes to object storage.
3a. Hot storage Only shown when tiered storage is on. Slider for days on local disk. tier days = retention − hot days.
4. Disk storage (TB per broker) Usable local disk on each broker, not the cluster total and not the broker count. Default 12 TB (Event Sizer recommended persistent volume). We recommend staying at 12 TB and not going over 16 TB. Changing this value recalculates broker count.

Fan-out, egress, NIC, and partition fields are not on the form. The model uses hidden defaults so the page stays as simple as Event Sizer’s primary controls.

Hidden defaults

  • Replication factor = 3; production floor = 4 brokers
  • Peak = average; egress = ingress
  • TLS on; utilization = 60%
  • 10 GbE (1250 MB/s), used at 60%
  • Disk IO = 1× SSD × 520 MB/s, used at 60%
  • Disk storage defaults to 12 TB per broker (user-editable)
  • CPU ≈ 120 MB/s produce per broker at 60% with TLS

Formulas

Brokers

brokers = max(4, network, disk_io, local_disk, cpu, RF)

Same shape as Event Sizer’s broker_recommended_count. The highest dimension is marked binding.

Storage

hot_GB = ingress × 1e6 × local_days × 86,400 × 3 / 1e9

storage_brokers = ceil(hot_GB / (disk_TB × 1000))

With tiered storage, local_days = hot_days and tier_GB = ingress × 1e6 × (retention − hot) × 86,400 / 1e9 (no RF on archival, matching Event Sizer).

Default example

50 MB/s, 7-day retention, tiered storage off, 12 TB per broker:

  • Local disk = 90.72 TB / 12 TB per broker → 8 brokers (storage binds)
  • Recommendation: enable tiered storage with 1 day hot → 4 brokers

How to use it

  1. Set peak ingress with the Throughput slider.
  2. Set how long data must be kept with Retention.
  3. Set usable disk storage per broker (default 12 TB). Do not go over 16 TB.
  4. If most reads are recent, enable tiered storage and set hot days. Tier days fill in automatically.
  5. Read “Why this many brokers” — it names the one limit that set the count.
  6. Compare with Event Sizer granular using the same throughput and retention.

Recommendation notes

Enable tiered storage

Shown when local disk needs more than 4 brokers. Event Sizer archives old data so brokers only hold the hot set.

Keep 4 brokers in production

Shown when HA is binding. Throughput would fit on fewer hosts, but RF=3 needs a spare broker.

Do not keep 7+ days only on local disk

Shown for long retention without tiered storage. Three copies of a week of data is usually the expensive part.

Network / disk IO / CPU

Shown only when that dimension is the max. Notes cite the Event Sizer default (60% utilization, TLS on, 10 GbE, 1× SSD at 520 MB/s).

Keep disk at or below 16 TB per broker

Shown when Disk storage is greater than 16 TB. The broker math still uses the number you typed.

Confirm before you buy

Shown above 50 brokers — the same warning Event Sizer uses.
